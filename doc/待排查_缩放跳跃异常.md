## ★ 排查结论（2026-10-06 当天已查清并修复，本文档留作记录）

**现象根因 = 方向 A 的变体（文档三/四节两个方向都不完全对）**：
"500ms 静默重载"**只挡不兜**——按住连按时缩放值每 150ms 变一次，
`zoom_quiet` 被不断清零 → 永远走不到 500ms → **重载根本不发起** →
系统空闲（位5=1）、画面死卡在旧图；松手后 500ms 静默 + 350ms 装载才跳到目标。
（方向 B 已排除：cfg_cdc 延迟 <1µs，重载发起时值已静默 500ms，
 img_scaler 采样必为新值；单次大跳变仿真也正常。）

**用户三问的答案**：① 卡住不动（非黑屏/花屏/错比例）② 按住连跑几十下 ③ 位5=1。
"位5=1"不是 B 的证据——重载没发起时系统确实是"空闲"的。

**修复**（`SD/sd_card_bmp.v`）：静默期加兜底 `ZOOM_FORCE_GAP`——
`zoom_pending` 置 1 后独立计时（连按不清零），满期还没重载就强制用当前值刷一次。
- 初版兜底 800ms：仿真 5/5，但**用户上板反馈"延迟很大很大"**（约 900ms 才跟一档）→ 已缩短
- **当前兜底 400ms**（2026-10-06 二次修改）：仿真 5/5（`tools/仿真_缩放跳跃.py`），
  按住 4.5s 连按 20 下 → 7 次重载（115→130→145→160→175→190→200），
  画面每约 450ms 跟一档（每档 15%），松手 ~750ms 到位；小步长行为不变。
  400ms 是下限：再小也会被 reload_ok 400ms 节流卡住；音频靠仲裁器扇区级
  "告急插队"（wav_urgent）不断音，SD 占空 ~64% 安全。

**上板验证点**（下次上板时顺手确认）：
按住缩放键不放连跑几十下 → 画面应每隔约 0.5 秒跟一档（明显比旧版快），
松手后 1 秒内到目标值；开着音乐调缩放，音乐不应断。

## 一、现象（用户原话）

**最近一次（2026-10-06）**：

> "我放大缩小步长很小的时候他是正常的，但是跳跃太大就会坏掉"

**更早一次（同一类问题）**：

> "连续调节还是黑屏后卡住了，然后在我调节的上一个缩放大小卡着，
>  但是不会出现数码管变成除了 1 以外的别的数字，
>  我等待很长的时间后他还是会到达我目标的放缩大小"

### 已经能确定的边界

| 操作 | 结果 |
|---|---|
| **小步长**（按几下，相邻两次缩放值接近）| ✅ 完全正常 |
| **大步长**（连按很多次 / 一次跳几十%）| ❌ 异常 |
| 异常后**等很久** | **能到达目标尺寸**（关键！说明不是死锁，是慢或者顺序错）|
| 异常时的数码管位5 | **是 `1`**（不是 0/2/3/4）|

**★ 这两条最关键**：
1. 数码管位5 = `1`（空闲）→ **说明系统没被复位、也没有卡在装载状态**；
2. **等很久能到达目标** → **不是死锁**。

## 二、★ 开工第一件事：向用户确认三个问题

**这三个问题必须先问清楚，否则会查错方向**：

| # | 问题 | 为什么问 |
|---|---|---|
| 1 | **"坏掉"具体是什么样？** 花屏 / 黑屏 / 卡住不动 / **尺寸不对但画面清晰** | 四种指向完全不同的原因 |
| 2 | **"跳跃大"是多大？** 一口气从 50% 调到 200%（连按 30 下），还是一下按七八次？ | 判断是不是"多次重载排队" |
| 3 | **坏掉时数码管最左位是几？**（已知上次是 `1`，再确认一次）| `1` = 系统正常但画面不对；`4` = 还在装载；`0` = 又被复位了 |

**⚠️ 特别要问清第 1 条**——"尺寸不对但画面清晰"和"花屏"是**完全不同**的两个 bug：

- **尺寸不对（画面清晰）** → 是**缩放比例参数**的问题（方向 B）；
- **花屏** → 是**数据通路**的问题（可能是 img_scaler 的行缓存错乱）。

## 三、两个怀疑方向

### 方向 A：多次重载排队（"慢"）

**机制**：用户连按时 `zoom_val` 快速变化 → 每次都置 `zoom_pending`。
如果**重载期间用户又按了**，那么重载完成后 `zoom_pending` 还是 1 →
**立刻再触发一次重载** → 排队。

**表现**：画面长时间黑屏/停顿，但**最终会到达目标**，数码管位5 会长时间停在 `4`。

**已有防线**（可能不够）：
- `reload_ok`：两次重载之间至少隔 400ms；
- `zoom_quiet`：数值变化后要 500ms 静默才重载（2026-10-06 加的"静默重载"）。

**要查的地方**：`SD/sd_card_bmp.v` 里"缩放值变化 → 重载"那段：
```verilog
if (I_zoom_pct != zoom_d) begin
    zoom_pending <= 1'b1;
    zoom_quiet   <= 27'd0;
end else if (zoom_quiet < ZOOM_QUIET_GAP) begin
    zoom_quiet <= zoom_quiet + 27'd1;
end
zoom_d <= I_zoom_pct;
...
else if (scan_done && bmp_ready && display_valid && !load_busy
         && zoom_pending && reload_ok
         && (zoom_quiet >= ZOOM_QUIET_GAP)
         && (img_found_count != 3'd0)) begin   // ← 这里是"缩放重载"分支
```

**可能的漏洞**：重载**发起时**清 `zoom_pending`，但如果用户在重载**期间**又调了缩放，
`zoom_pending` 会重新置 1，重载完成后**立即再重载**一次 → 反复。

---

### 方向 B：img_scaler 采样到"旧值 / 中间值"（"比例错"）

**机制**：缩放值的传递链是
```
按键 → key_ctrl_fsm.zoom_val → O_zoom_pct
     → cfg_cdc（跨时钟域，翻转握手）→ cfg_zoom_pct_sd
     → sd_card_bmp.I_zoom_pct → img_scaler.I_zoom
```
而 `img_scaler` **只在 `I_frame_start` 那一拍采样**这个值：
```verilog
S_IDLE: begin
    ...
    if (I_frame_start) begin
        tmp_num <= {24'b0, zoom_use} * 32'd24;   // ← 就在这一拍读 zoom_use
        ...
    end
end
```
如果那一拍新值还没稳定传到，就会**用旧值算整帧的缩放比例** ——
画面会**清晰但比例明显不对**（不是花屏）。

**表现**：画面清晰、但尺寸不是目标值；数码管位5 = `1`。

## 四、怎么区分 A 和 B

| 观察 | 方向 A（重载排队）| 方向 B（参数采错）|
|---|---|---|
| 数码管位5 | 长时间停在 **`4`**（装载中）| **`1`**（空闲）|
| 画面 | 黑屏 / 停顿 | **清晰但比例不对** |
| 等很久后 | **会**到达目标 ✅ | **不会**自动变（一直错）❌ |
| 音频/字幕 | 正常 | 正常 |

**⚠️ 根据用户最后一次描述**："等很久能到达目标" + "数码管是 1" —— **两条信息互相矛盾**：

- "能到达目标" 更像 **A**（慢，但会完成）；
- "数码管是 1" 更像 **B**（系统空闲，画面已切换，但比例不对）。

**所以第一个要问的就是第 1 条："坏掉"时画面是黑屏还是清晰的错比例** —— 这一条能直接分开 A 和 B。

## 五、排查手段（不需要上板）

### 如果是方向 B → 写逐拍仿真

在 `tools/` 下新写一个 `仿真_缩放跳跃.py`：

1. 造一个源图（坐标图案，便于反解）；
2. 用几个**相邻但差异大**的缩放值序列（例如 200% → 50%、50% → 200%），
   在**连续两帧**之间切换；
3. 逐拍跑 `img_scaler`（严格按 RTL 翻译，含块 RAM 读延迟、`EMIT_DIV` 分频）；
4. 检查每一帧输出的**比例**是否正确（例如输出图像的实际内容边界）。

**现成的参考**：`tools/仿真_端到端.py`（连续 3 帧、逐像素比对，已经能跑）。
把它改造成"帧间缩放值大跳跃"的版本即可。

### 如果是方向 A → 数重载次数

在仿真里统计"一次连续操作触发了多少次重载"（`load_busy` 的上升沿次数）。
`tools/仿真_缩放重载.py` 已经验证过"重载决策逻辑"，可以扩展它。

## 六、当前系统状态（背景）

### 已经修好的（2026-10-06）

- `O_frame_start` 判断偏移（`pixel_offset + 3`）
- img_scaler 突发输出导致写 FIFO 溢出（S_EMIT 加 4 分频）
- `next_from_current` 位宽截断（2 位 → 3 位）
- `O_frame_start` 拉长成 8 拍电平（抗错过）
- `rst_n` 20ms 消抖 + PLL lock 1ms 滤波（消除噪声误复位）
- 静默重载（缩放变化后 500ms 才重载）
- 装载超时 30 秒（原 2.7 秒比实际装载还短）
- SD 初始化加 100ms 上电等待
- 三个通道扫描范围**统一为 64MB**（曾缩到 16MB 导致 23.8MB 的 WAV 找不到 → 没声音）

### 用户确认可用的功能

- ✅ 图片显示、切换、自动轮播
- ✅ 音乐、字幕
- ✅ 缩放**小步长**调整
- ⚠️ 缩放**大步长**调整（本文件要查的）

### 关键约束（不要违反）

| 约束 | 说明 |
|---|---|
| WAV 必须 48000Hz / 16bit / 立体声 / PCM | HDMI 音频时钟（ACR）决定 |
| 扫描范围不能小于 64MB | 大文件（24MB 的 WAV）的文件头可能很靠后 |
| BRAM 余量约 62/64 块 | 不要再加块 RAM |
| 信号必须声明在第一次使用之前 | HDL-7225 隐式线网坑 |
| 视频流水线每级都要补 `video_sync_delay` | 否则画面偏移 |
